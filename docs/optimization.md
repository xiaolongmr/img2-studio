# 性能优化记录与后续计划

本文档用于同步当前二次开发版本的性能优化现状，重点关注图片工作台与提示词库。

## 1. 已完成的优化

### 1.1 历史记录侧栏渲染压力优化

- 会话列表改为分批可见（首屏有限条目 + 滚动增量加载）。
- 历史卡片启用 `content-visibility: auto`，降低离屏 DOM 的布局/绘制成本。
- 历史预览图增加缩略图生成与缓存：
  - 对大图（尤其 Base64）进行降采样；
  - 缓存缩略图并限制缓存上限，减少重复解码。

### 1.2 对话内容区渲染优化

- 对话 turns 增加分段加载（先展示最近记录，按需展开更早记录）。
- turn 卡片同样启用 `content-visibility: auto`，降低超长会话切换时的首帧压力。

### 1.3 提示词库列表性能优化

- 提示词卡片采用分批渲染（chunk + IntersectionObserver）。
- 过滤/搜索与可见条目切片解耦，减少一次性渲染全部卡片造成的卡顿。

### 1.4 图片响应体策略优化

- 请求时优先使用 `response_format`，并在上游不支持时自动回退。
- 数据归一化时优先保留 `url`，减少不必要的 `b64_json` 持久化体积。
- 在流式场景下支持中间步骤图回调，不阻塞最终图落地。

### 1.5 交互链路优化

- 参考图支持拖拽上传，降低上传操作路径成本。
- `@图N` 引用增强，减少手工输入错误与重复编辑。

## 2. 当前仍存在的主要瓶颈

### 2.1 大会话切换仍可能卡顿

当会话内图片很多且包含大量 Base64 数据时：

- 数据反序列化成本高；
- 图片解码与布局成本高；
- 切换会话时主线程仍会有明显压力。

### 2.2 高频轮询带来的 UI 抖动与开销

当前存在较高频率刷新逻辑（如任务轮询、历史刷新），在任务并发时会导致：

- React 状态更新频繁；
- 不必要的重复排序/合并；
- 页面交互手感变“粘”。

### 2.3 本地存储体积增长快

会话长期累积后，若大量图片以 Base64 形式保留：

- localforage 存储体积快速增大；
- 冷启动与切换成本上升；
- 浏览器存储稳定性下降。

### 2.4 图片解码时机仍可更细化

虽然已有懒加载，但在某些长列表场景中，仍可能出现同屏多图同时解码导致掉帧。

## 3. 下一步优化计划（按优先级）

### P0（优先落地）

- 将会话列表预览固定为小尺寸缩略图源，避免侧栏回退使用原图。
- 为 Base64 历史图增加后台惰性转存策略（可转 `Blob URL` 或文件化缓存）。
- 降低高频轮询抖动：
  - 有活跃任务时采用自适应轮询（快 -> 慢）；
  - 无活跃任务时停止轮询。

### P1（中期）

- 对会话详情区做“虚拟化窗口渲染”（仅渲染可视区附近 turn/image）。
- 历史与详情切换增加过渡占位骨架，减少白屏感和跳变。
- 将图片元数据与大体积内容拆分存储（索引快读 + 内容按需取）。

### P2（长期）

- 引入后台 Worker 处理缩略图与重编码，进一步释放主线程。
- 统一构建“图片缓存层”（生命周期、清理策略、容量上限、命中统计）。

## 4. 验收指标建议

可用以下指标作为每次优化验收标准：

- 切换会话首帧：目标 < 200ms（中等会话量）。
- 历史侧栏滚动：连续滚动无明显掉帧。
- 任务进行中 UI 响应：输入与点击无明显阻塞。
- 大量会话下冷启动：明显优于当前基线。

## 5. 维护建议

- 新增功能前先定义“数据体积预算”（单会话、单图、总缓存）。
- 任何新增图片字段都应评估是否会放大本地存储。
- 保持“可观测性优先”：记录关键链路耗时，避免优化后回归不可见。
